# 隐蔽破坏点（`Features/Host/ShadowSabotage/`，纯服务端）

两个**伪装成小熊**的服务端破坏点。破坏与修复都走原版摇汽水条（物品 1039 / 满值 24 / 100ms 自续链），
**打断保留进度**。本文是这一功能的机制地图与坑清单；规则红线条目见 `AGENTS.md`。

## 0. 口径（2026-10-18 二次定案，以本节为准）

1. **谁能操作**：未破坏时只有黑幕（`EPlayerColor.Dark`）；破坏后**所有人（含黑幕）**可修 ——
   黑幕可以立刻撤销自己刚做的破坏，这是允许的（口径明确）。
2. **单点生效**：我们的破坏不需要像原版电闸那样凑两个才算数。
3. **破坏期间封锁一切其他破坏**（含原版电闸）：
   - 另一个破坏点同时进 CD（`LockAllBreakers`），既拿不到假主人（`IsEligible` 的 `AnyBroken` 守卫）、
     也不会被 CD 逻辑放行；
   - 原版电闸窗口**整体作废**：`DeviceManager.ClearFuseboxSabotage()`（:166838）把三个电闸的
     `MissionType` 清回 0，并撤掉它们的图钉 / 平板条目；`Fusebox.DisconnetCable` 自己也要求
     `MissionType == -1`（:165646），所以谁都拉不动。
4. **CD**：**破坏结束（修复完成）后 60 秒**到点重派发。计时器由本模块自建
   （`TimeManager.PushSurvivalJob(60, ReopenWindow)`）—— 我们的破坏**不动光照**，等不到原版
   `RefreshLight` case 0 那条信号（:176585）。到点时若场上仍有电箱未恢复供电，则**不**重派发，
   交给原版供电恢复流程。
5. **线索**：**每次完整破坏都追加一条**「黑幕 于 … 在本房间 切断了电力」，
   语义与原版电闸 `RecordLastUsingPlayer(player, EWhatState.Mastermind)`（:166386）对齐：
   `PlayerId = 11037` + 当刻 `SurviveTime` + 本设备房间 + **30 秒窗口内合并**（跨窗口追加）；
   另外给操作者本人补一条 `S_LEFT_CLUE{RoleFace = true}`。修复**不撤**线索
   （"破坏点到了调查阶段可被任何人调查"是需求，不是 bug）。
6. **通知**：破坏 +10 秒给所有存活者发断电箭头（`FuseboxArrow`），**刻意不发任何文字通知**；
   若 10 秒内被修复则不发光标（`SendArrow` 自校验 `Broken`）。
7. 破坏点留到调查阶段，**任何人**都能扫出那条线索；CD 中与破坏中**小熊本体始终在场**（只是没图钉、不能交互）。

## 4. 十个必须记住的坑

1. **设备 ID 取 90 万段**（`900101` / `900102`）。客户端按 `DeviceDic` 是否命中决定 prefab，
   ID 命中就会变成别的设备外观；而 `ObjectUtils.GenerateNewId()` 从 16 起递增、**每局 `Clear()` 还会重置** ——
   我们的设备跨局常驻，用它迟早撞车。
2. **`StateList` 必须恰好 2 槽**：`[0]` = 0 正常 / **2 已破坏**（避开 `1` —— `1` 会触发范围圈
   `ShowRange` 与麦克风静音 `MuteMicWorld`），`[1]` = 假主人位。进度 / CD / 伪装名单一律放服务端字典。
3. **不走 `DeviceManager.CreateSummon`**：一旦进 `_summons` 就会被凛的附身技能
   （`PossessMarionette` → `GetSummon`）认领。我们直接 `SpawnDevice`。
4. **两个污染钩子的 `[HarmonyPriority]` 不能省**（与本模块 `RecordDetail` 抢同一个方法）：
   身份 `Priority.First`（`RecordDetail.RecordHook` 要看到改过之后的值，旁路表键才对得上）；
   时间 `Priority.Last`（要**晚于** `BroadcastHook` 的查表与 `ScanHook` 的补详细活动）。
5. **必须拦 `ItemManager.DropItem` / `AcquireItem`**：客户端 `DropHand` 是**先本地清手再发包**，
   放行会让玩家把**真物品**丢地上、进度条同时消失（两个钩子只在 `BreakBar.IsActive` 时生效）。
6. **广播会冲掉假主人**：`BroadcastState()` 带出去的是权威 `DeviceInfo`（`StateList[1] == 0`），
   所以每次广播之后必须让伪装名单失效并立刻重发（`Finish` / `OnWindowStart` 都做了）。
7. **"能不能操作"由客户端 ±75 交互框决定，不由服务端 `InteractRadius=120` 决定。**
   落点若贴墙 / 压在摆件上，玩家进不去那个矩形 ⇒ 没有「按 E」、也就点不动。
   **⚠ 但"科学室那只点不到"至今没有结论**：地图数据里 `(6608,4700)` 所在格
   （GX=25 / GY=15，以及同列 GY 12–16）全是 `scan_room_tile`（**地板**，不是墙）——
   所以"贴墙"只是猜测。**实测必须先测现坐标，再谈搬哪儿。**
   **实机验证手法**（DT_Tools MCP，不用重编重部署）：
   1. `beacon <x> <y>` 把被测玩家挪到落点；
   2. 对**他本人** `call_s #<id> S_MODIFY_DEVICE` 单发一条 `StateList[1] = 该玩家` 的 `DeviceInfo`
      （就是 `RefreshFakes` 干的事，可用来排除"假主人没送到"）；
   3. `shot` 截图看是否出现「按 E」提示；
   4. 若**现坐标**就有提示 ⇒ 说明"点不到"是别的原因（别急着挪）；若确实没有 ⇒ 再按
      「同列地板格」依次试候选，选定后才写进 `PosIdentifyX/Y`。

   **可直接粘贴的测试序列**（示例：房主 #1 在科学室，设备 900101）：

   ```
   beacon 6608 4700
   call_s #1 S_MODIFY_DEVICE {"info":{"deviceId":900101,"bubble":0,"stateList":[0,1]}}
   shot 1280
   ```

   ⚠ **JSON 必须是 protobuf 的 camelCase**（`call_s` 的 PJ 解析规则见其自带帮助：
   "字段名以 protobuf JSON 为准（多为 camelCase）"）。`{"Info":{"DeviceId":…}}` 这种 PascalCase **发不出去**。
   `info` 里只给 `deviceId` / `bubble` / `stateList` 就够：客户端 `Managers.Device.Modify`（:27850）
   只读 `Bubble` / `MissionType` / `StateList`，而这三项本来就该保持服务端真值（0 / 0 / `[0, pid]`）。
   （这条命令已在大厅**干跑验证**过：JSON 解析通过、包能发出 ✓。）

   **候选点**（科学室最左列 GX=25；`MapByte` 行 X=25 在 GY 14–17 全是房间 12，`TileData` 同列均为地板）：

   | 编号 | 坐标 | 说明 |

   - ⬜ A 现坐标：待测（游戏一直在大厅，没轮到 Survive）。
8. **时间污染绝不要改 `Time` 真值**（30 秒去重窗口会碎）；正确做法是「写入时打未知字段 **101** +
   在 `HostPeerSession.Send` 的出站副本上替换」，见 `docs/线索机制.md` §4。旧写法（改 `S_ADD_CLUE` 包、
   整替 `Device.Scan`）**对界面完全无效** —— 界面时间来自 `S_SCAN_DEVICE` 与 `S_ADD_MY_CLUES`。
9. **窗口封锁有四处实现点，少一处就漏**：`Finish` 置 `CanBreak=false` → `OnStateChanged` 的

   `BreakerStates.AnyBroken` 守卫 → `OnWindowStart` 用「设备是否已被 `DeviceManager.Init()` 清掉」

10. **我们关掉的窗口必须还回去**：热关闭（`OnDisabled`）与重派发被拒时都要
    `StartFuseboxSabotage()`（且 `GetDisconnectFuseCount() == 0` 才做），否则这一局剩下的时间
    黑幕连电闸都拆不了。

### 7.1 与电闸的互锁：单台电闸会把破坏点锁死（2026-10-21 修）

**现象**：先拉掉一台电闸、再破坏小熊、然后修好小熊 → 两个破坏点**永久不可破坏**。

**根因是两段机制叠在一起**：

1. `ReopenWindow`（`Logic.cs`）在 CD 到点时，只要 `GetDisconnectFuseCount() > 0` 就 `return`，
   理由写着"交给原版供电恢复流程"；
2. 而原版那条链只在**供电全部恢复**时触发（`AreaManager.RefreshLight` 的 `case 0`，:176585）；
3. 单台电闸坏着时它**永远恢复不了**：
   - `RefreshLight` 走 `case 1`、不置 `Area.IsLight = false`；
   - 客户端 `Fusebox.GetInteractMessage`（:3244）要求 `Managers.Game.Darkness`，
     而 `Darkness = !Area.IsLight`（:30610 / :30628）；
   - 服务端 `ConnetCable` 的守卫同样是 `!Area.IsLight`（:165624）。

⇒ 客户端不给修复提示、服务端也拒绝修复。原版的设计是"拉满 2 台才全图断电、才修得了"，
我们的破坏点却把这个中间态当成了重开的前置条件。

**修法（方案 A，已落地）**：把小熊修复与电箱复位**绑在同一刻**。

- `OnStateChanged` 的修复分支（④.5）：先 `ForceRestoreFuses` 把没恢复的电箱**当场复位**，
  再 `ScheduleReload()` 起 60 秒 CD；
- 也就是说"破坏结束"与"多久后能再拆"是两件事 —— 修复瞬间灯就亮、闸就好，
  CD 只负责压住下一次窗口；
- `ReopenWindow` 里保留一次同样的检查，纯兜底（CD 期间若又有人拉断一台，到点时一并复位）。

`ForceRestoreFuses` 的实现要点：

- 复位前先把该区域 `Area.IsLight = false`，否则 `ConnetCable` 的守卫不成立、什么都不会做；
- 复位走 `ConnetCable()` 自己的收口（`IsLight=true` / 撤箭头 / `StateList[0]=0` / `InitProgress` / 广播）；
- 这些电闸**确实是黑幕拆的**，但原版对「只拆一台」没有自愈路径（见上面的机制链）——
  不处理它们，下一次派发就会被「供电未恢复」卡住，所以只能强制复位。

⚠️ 最初把这步写在 `ReopenWindow`（CD 结束时）里，实机口径不对：那 60 秒里玩家看到的仍是
"灯灭着、闸坏着"，与小熊已修好的状态矛盾。**复位必须在修复那一刻**。

**方案 B（已评估，不采用）**：让小熊与坏掉的电闸**绑在一起修**——
小熊修好后仍不算结束，补发箭头、每秒检查，全部电闸修好才重开窗口。

不采用的理由：要让客户端电闸进入"可修复"，必须把**那间房的 `Area.IsLight` 置 false**
（见上面的机制链 3），也就是**让那个房间当场变暗**。一个自定义破坏顺带把一间房弄黑，
观感与语义都不合适；而且它把"小熊修好了却还没结束"这个中间态暴露给玩家，容易误判。
如果将来一定要做，必须同时解决"房间变暗"的表现问题。

## 6. 科学室落点：为什么按不到 E，以及新落点（2026-10-19）

**旧默认 `(6608,4700)` 走不过去 / 按不到 E 的根因**：它**本身就在 `Shelf` 的实体碰撞盒内**
（该 BoxCollider2D：x[6590.3, 6951.7] y[4493.9, 4784.4]，非 trigger），最近设备
`StorageBattery(6701,4738)` 仅 100 单位 —— 两件事叠在一起，玩家既站不进去也点不到。

**地图实测（用安装目录 0.1.18 的 `school_data`/`school_prefab`，脚本在 `.tmps\mapsolve\`）**：

```
世界格 wt = (floor(X/224), floor(Y/224))        # 与 TileData 的 Pos 一致
MapArray 下标 = (wt.x-4, wt.y-5)                 # MapOffset=(4,5)，896=4*224、1120=5*224
格中心 = ((wt.x+0.5)*224, (wt.y+0.5)*224)        # X/Y 同一套，无 Y 翻转
```
验证：① 129 台固定设备里 128 台按此公式落格与自身 `RoomType` 完全一致（唯一例外在地图外）；
② `Science` 瓦片的 47 格 == `MapByte` 房间 12(ScienceRoom) 的 47 格（完全相等）；
③ 0.1.17a 与 0.1.18 的 `MapByte`/`TileData` 逐格一致（0 差异）。

**科学室的可走带**：东西向过道 y≈**4790~5120**（瓦片全 `Science`、无碰撞盒），
南边是 700×336 的墙盒（y[4256,4592]）、北边同样一块（y[5152,5488]），
**西口被 28 厚竖墙封死**（x[6482,6510]，y[4144,5488]）⇒ 科学室全图只有两扇门
（`DoorCleanHR (7168,5145)` 通 ScienceCorr、`DoorCleanHR (8064,3577)` 通 ScienceHall/ComputerRoom），
**西端无门 ⇒ 那里是死头**，正是"最左边的过道终点"。

**新默认落点 = `(6580, 4900)`**（世界格 29,21）：过道最西端、离墙 70、最近设备
`Bio(6730,5033)` 净空 200.5，从东门进来向西直行即到。
备选：`(6600,4900)`（离墙 90、净空 186，稍里一点）、`(6570,4960)`（离墙 60、净空 176）。

⚠️ 碰撞盒里含 2.5D 墙面体，**仍需实机目测一眼**；位置随时可在 CONFIG 页改
（`[ClueShadowSabotage] PosIdentifyX/Y`，代码每秒校验一次位置、不一致就重建小熊）。
