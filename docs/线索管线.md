## 2. 优先级阶梯（`Core/ClueWhat.cs:35-128`）

**同一份线索数据，取"详细活动"的顺序如下（上一级命中就不再往下走）**：

| 级 | 出处 | 命中条件 | 取到的文本 | 谁会走这一级 | 失败/不命中时 |
| --- | --- | --- | --- | --- | --- |
| ⓪ 守卫 | `ClueWhat.cs:62-66` | `Define.IsDestroyEvidenceClue`（:95774）= `PlayerId ∈ {11038, 66613}` | **保持原版**「销毁了证据」 | 所有人 | 不适用（有意短路） |
| ① 包内未知字段 100 | `ClueWhat.cs:69-75` | `UnknownFields.GetWhat(info) != 0` | `EWhatType` → `Managers.GetText(EWhatType 名)` | 房主开了 `BroadcastDetail` 的**全体**（未装模块端忽略该字段，照旧显示原版） | 字段缺失 → ①.5 |
| ①.5 房主旁路表 | `ClueWhat.cs:83-92` | `RoomState.IsHost && DetailStore.Recall(...) != 0` | 同上 | **只有房主本机**（它不走镜像） | 换局清空 / Time 被改写 ⇒ miss → ② |
| ② 设备关联 | `ClueWhat.cs:95-102`；`Core/ActivityMap.cs:106-133` | `ActivityMap.DeviceOf(...) != 0` 且设备 `WhatType != WNone` | 设备表里的 `WhatType` | 客户端：见过该线索的 `S_ADD_CLUE`，或**自己扫过**那台设备 | 关联丢失 / 设备 WhatType 为 WNone（例：伪装小熊是 Summon） ⇒ ③ |
| ③ 房间唯一设备 | `ClueWhat.cs:111-123`；`Core/RoomDeviceScan.cs:25-70` | `CandidatesOf(room)` 去重后**恰好 1 种** | 该唯一活动 | 房主没装 / 包丢了 / ② 拿不到，但房间只有一种活动 | 0 种 → 全失败 |
| ④ 房间多设备 | `ClueWhat.cs:125-127` | 去重后 **≥ 2 种** | **通用文案**「操作了设备」（`Localization.cs:20/33`） | 同上 | — |
| — 全失败 | `ClueWhat.cs:114-116` / `:105-109` | 以上都空（或自采集关、本局禁用） | **保持原版**：`{what}` 段不替换 ⇒ 角色级两选一「切断了电力 / 销毁了证据」 | 所有人 | 这是**最低兜底**，也是 ⓪ 之外的"没还原"状态 |

- **最高优先级 = ①（服务端精确下发）**；**最低兜底 = 不替换**（原版角色级文案），④ 是"可判明房间但判不明设备"的软兜底。
- 每一级都会经 `Diagnostics.TraceClue`（`Core/Diagnostics.cs:168-187`）打一行来源，行里直接写明走了哪一级。
- 各级都会经过的开关：`RoomState.AllowDetail`（`:50`）→ 本局禁用就整条不还原。

## 3. 渲染路径（从包到屏幕上那串字）

```
服务端 ClueList ──(S_ADD_CLUE/S_SCAN_DEVICE/S_ADD_MY_CLUES)──> 客户端
   ├─ S_ADD_CLUE  → ClueMirror(设备→线索)  (:43621-43627，房主端被短路)   ← 只喂 DeviceBase 渲染，不喂平板列表
   ├─ S_SCAN_DEVICE → ClueManager.TakeDeviceClue (:27588) → AddClue(:27600)/AlreadyExistClue(:27607) → 平板列表
   └─ 平板行 UI_ClueSubItem.SetInfo(Clue) (:86504) → clone Info(:86512) → Refresh(:86562) → FillText(:86635)
最终字符串 = ①卡片槽位文本（who/房间/时间，FillText 逐槽填）  ②悬浮整句（Util.FormatProposition）  ③伪证行同构槽位
```

### 3.1 句子怎么拼出来（`Util`）

- `FormatProposition`（:27343）→ `GetPropositionSentence`（:27510）取**模板**：
  `Managers.GetText(CharacterDic[OwnerCache.CharacterId].Name + (IsRoleClueId(Info.PlayerId) ? "PropositionSentenceRole" : "PropositionSentence"))`（:27514）。
  ⇒ **模板由 `OwnerId`（谁说的）决定**，外加一个"是不是角色线索"的后缀（`Define.IsRoleClueId` :95765 = `IsMastermindClueId`(11037/11038，:95756) 或 `66613`）。
- 然后正则 `\{([^}]*)\}`（:27346）替换四个占位符：
  `who`（角色 id 特判 + `WhoMastermind/WhoBlack/WhoSomeone` 或玩家名，:27352-27366）、
  `when`（`FormatTimeSentence(Time)`，:27367-27369）、
  `where`（`RoomDic[RoomId].Type` → 房间词条，:27370-27377）、
  **`what` = `<#FF97AB>` + `GetText(GetRoleWhatKey(PlayerId))` + `</color>`**（:27378-27380；`GetRoleWhatKey` :27517-27524 = 11037→`WhatCutPower`，其余→`WhatDestroyEvidence`）。
  ⚠️ **2026-10-19 定案（前两次结论都错，这次拿 0.1.18 运行时文案核的）**：句子模板是**两族**，且
  **普通线索那一族在文案层就把 `{what}` 删了** —— 所以上面那个 `case "what"` 分支**只在角色线索上会跑到**：

  | 模板 id | 何时用 | 0.1.18 中文文案 | 有 `{what}`？ |
  | --- | --- | --- | --- |
  | `PropositionSentence{角色}` | **普通线索**（`IsRoleClueId == false`） | 「…在{when}\n**位于{where}**。」 | ❌ **没有** |
  | `PropositionSentenceRole{角色}` | **角色线索**（11037/11038/66613） | 「…在{when}\n**于{where}{what}**。」 | ✅ 有 |

  ⚠️ 查证方法（关键）：语言资源在 **`language_assets_all_*.bundle` 的 `CHS_TextData`**（运行时真正加载的那份）；
  `data_assets_all_*.bundle` 里也有一份 `TextData`（507 条，**旧版残留**，含 `{what}`）—— **拿它核对会得出相反结论**
  （本模块 10-18 就是这么误判成"模板没删 {what}"的）。
- 我方在**这个方法之后**动它：`ClueWhat.TryDecorate`（`Core/ClueWhat.cs`）分两路：
  - 句子里有 `<#FF97AB>[^<]*</color>`（角色线索）⇒ **替换**那一段；
  - 否则命中「位于{where}」（普通线索）⇒ **把「位于」还原成旧版的「于」，并在地点后插入活动**
    （等价于 0.1.17a 的「于{where}{what}。」句式）。`ambiguous` 时用通用文案。
- `TestFormatProposition`（:27386）是**另一套**（`who` 分支不同、不查 `GetPlayerCache` 特判），调用点也不同（见 §3.5）。

### 3.5 同一份线索数据 → 不同句子的分支清单

1. **模板随 `OwnerId` 变**（:27514）：换个说话人/角色就是另一套句式。
2. **`IsRoleClueId(Info.PlayerId)` 决定后缀**（`PropositionSentenceRole` vs `PropositionSentence`，:27512）。
3. **`FormatProposition` vs `TestFormatProposition`**（:27343 / :27386）两套实现；调用点：
   正式版用 :72321（聊天/命题消息）、:73517、:73849 / :73897（审判侧文本）、:74943（按 `\n` 切分）；
   测试版用 :19267、:19646、:74981。
4. **`IsStatement`（伪证行 vs 线索行）**：切 `GetObject(1)/(2)`（:86568-86569），`OwnerId` 的含义也随之变。

## 5. 已知缺口与脆弱点（按风险排序）

**[✅ 2026-10-19 已修]** **F1（最脆弱，会产出**错**文本）· 角色线索没有被排除在"活动替换"之外。**
`ClueWhat.TryResolve` 的 ⓪ 守卫只挡 `IsDestroyEvidenceClue`（11038/66613，`Core/ClueWhat.cs:62`；游戏 :95774），
**没有挡 11037**。而破坏点线索正是 `PlayerId = 11037`（`ShadowSabotage/Logic.cs:1216`，`Time/RoomId` 之外无任何字段），
于是阶梯会一路下沉：① 无字段 → ①.5（`PlayerId=11037` 在旁路表里通常无记录）→ ② 设备是伪装小熊（Summon，`WhatType = WNone`）
→ **③ 房间唯一活动**（把「切断了电力」改成那台设备的活动）或 **④ 通用文案**「操作了设备」。
同一路径也适用于原版撤电闸造的角色线索。修法很小：在 `TryResolve` 里加一句
`if (Define.IsRoleClueId(clue.Info.PlayerId)) return false;`（与 ⓪ 同级），并让 `ClueCard` 的卡面也别猜（`Logic.cs:479-483` 已有一半保护）。

**F2 · 未知字段通道依赖对 `Google.Protobuf` 私有成员的反射。**
`Core/UnknownFields.cs:229-300` 反射 `_unknownFields`/`fields`/`GetOrAddField`/`varintList`；
换 protobuf 版本或换编译器就可能**静默失效**（写法是"能读回 0 就算没写"）。缓解：`SelfCheck` 启动时真写真读一次（`Core/Diagnostics.cs:76`）。
另：`SetWhat` 幂等（`:84-87`，靠调用点判 `GetWhat == 0`），要覆盖必须用 `ReplaceWhat`（`:101-110`）。

**F3 · ①.5 按 `(PlayerId, Time, RoomId)` 查旁路表，一旦 Time 被改写就会 miss。**
房主侧渲染若拿到的是"出站时间替换后"的副本（破坏点期间 `Time` = 冻结值），`DetailStore.Recall`（`ClueWhat.cs:85`）必然查不到，
只能靠 ①（字段 100）兜住 —— 也就是说**字段 100 缺失 + 时间污染同时发生**时，房主会掉到 ②/③。

**F4 · `<#FF97AB>` 色号硬依赖。**
`ClueWhat.cs:208-209` 的正则认的是 0.1.18 的固定色号；官方改色号或改 `{what}` 的渲染方式 ⇒ 替换**静默不生效**
（界面上就是"没有详细活动"），日志里只表现为 `来源=…` 但不改文本。

**[✅ 2026-10-19 已修]** **F5 · `ActivityMap` 的房号配对可能张冠李戴。**
请求被拒（旁观者、非 Survive）时不会有响应，而 `MatchesPendingRoom` 只校验队首房间（`ClueRender/Patch.cs:120`、`Core/ActivityMap.cs:60-92`）：

**F6 · 迁移快照丢字段 101。** 迁移来的老线索显示真实时间（可接受，已在 `docs/线索机制.md` 备案）；字段 100 保留 ⇒ 活动不受影响。

## 8. 污染对**显示**的影响（2026-10-19 补，逐段对照代码）

`Util.FormatProposition`（0.1.18 :27343）逐段取数：`{who}` → `GetPlayerCache(PlayerId)`；`{when}` →
`FormatTimeSentence(clue.Info.Time)`；`{what}` → `Managers.GetText(GetRoleWhatKey(PlayerId))`；`{where}` → 房间类型词条。

## 10. 决策记录：污染线索的"可分性"够用即停（2026-10-19）

**需求（用户口径）**：不需要"匿名与实名各成一条 + 每代一条"那么细，**只要能分开"破坏期间写出"与"破坏之外写出"的线索**即可。

**结论：当前实现已满足，零代码改动。**

| | 破坏期间写出的线索 | 破坏之外写出的线索 |
| --- | --- | --- |
| 真值 `PlayerId` | **0**（身份污染 `state → Anonymity`，`ShadowSabotage/Patch.cs:200-213`）⇒ 渲染「某人」 | 真实玩家 id ⇒ 实名 |
| 未知字段 **101**（显示时刻） | **有**（冻结在破坏那一刻） | 无 |
| 30 秒合并键（`Time >= limitTime && PlayerId == playerId && !Destroyed`） | 含 `PlayerId=0` | 含真实 id ⇒ **两者不同键、互不覆盖** ✓ |
| 特殊行动线索 | `11037`（切断电力）/ `11038`·`66613`（销毁证据）自带角色身份 | — |

**推荐判据（给将来的消费方）**：优先 `UnknownFields.GetDisplayTime(info) != 0`（字段 101 只在污染窗口内打，语义就是"破坏期"）；
`PlayerId == 0` 目前等价，但语义只是"匿名"（将来别处若也用 `Anonymity` 就不等价了，且原版从未使用过该状态）。
`Define.IsRoleClueId(PlayerId)`（:95765）用来判"特殊行动线索"。

**暂缓项（本次刻意不做，记在案）**：
1. **代次封印**（方案 ④）或**整替 `RecordLastUsingPlayer`**（方案 ③）—— 目标是把 A（破坏前）/ B（破坏期）/ C（修复后）拆成三条；
2. 出站按收件人匿名（当事人看实名、其他人看「某人」）+ 出站把编码 id 解码回实名；
3. 字段 102 = 来源设备号 / 服务端 per-player「已获得线索」表；
4. 污染期**强制补字段 100**（用于修"未装模块的端 / 房主关掉 `BroadcastDetail`"时 `{what}` 退化成「销毁了证据」）。

**已知且接受的副作用**：
- 破坏期内**不同的人**会被合并成同一条「某人做过」（键里 `PlayerId` 都是 0）；
- 修复后的正常使用会与"破坏前同一个人"的线索按**原版 30 秒桶**合并（这是原版行为，不是本次改动引入）；
- 未装本模块的端在污染期会看到「销毁了证据」（0.1.18 `GetRoleWhatKey` 对非 11037 一律该词条；原版从未产生过 `PlayerId=0`）。

**版本核对结论（同节备查）**：0.1.17a 与 0.1.18 的 30 秒桶判定**逐字相同**
（`0.1.17a :165655-165656` / `0.1.18 :166404-166405`），调用点各 **49 处、集合一致**；
唯一差异是客户端"同一条线索"的判定：0.1.17a 多比一个 `WhatType`（:27570 / :181502），
0.1.18 因字段被删只剩 `(PlayerId, RoomId, Time)`（:27611 / :182260）—— 我们的 `ActivityMap` 键正是这三样 ✓。

## 11. 新增开关与修复（2026-10-19 晚）

### 11.1 `[ClueRenderDetail] DistinctByActivity`（新，默认 `true`）

**问题**：线索身份的判定维度少了"活动"这一项。
- 0.1.17a：`ClueManager.AlreadyExistClue`（:27570）比较
  `PlayerId && RoomId && Time && **WhatType**` ⇒ **活动不同就各留一条**；
- 0.1.18：字段被删，只剩 `(PlayerId, RoomId, Time)`（:27611）⇒ 活动不同的两条会被当成同一条、后到的被丢弃。

**为什么现实里真会撞**：时间污染把多条线索的**显示时刻**改写成同一个冻结值（我们改的是包里的 `Time`），
于是"同一人 + 同一房间 + 不同设备"的两条线索在客户端看起来三元组完全相同 ⇒ 若活动也不参与判定，就只剩一条。

**做法**（`Features/Client/ClueRender/Patch.cs` 的 `ActivityIdentityHook`）：
只在**原版已判定"重复"**时介入 —— 若那批同名候选里**没有任何一条与它活动相同**，才改判为"不存在"，
调用方于是另起一条。活动身份取：字段 **100** →（没有则）字段 **101** 的显示时刻 → 0。
⇒ 开关关掉时完全回到 0.1.18 口径；开着等于把 0.1.17a 那一维补回来。

### 11.2 跨局残留修复（`ActivityMap` / `DetailStore`）

**问题**：两张内存表的键里都带 `Time`（`SurviveTime`，**每局从 0 重算**），而它们的 `Clear()`
**此前从未被任何地方调用** ⇒ 上一局的 `(人, 时刻, 房间)` 会命中这一局的线索：
客户端 ② 设备关联可能查到**上一局那台设备**的活动；房主 ①.5 旁路表同理。

**做法**：加 `ResetIfNewRound(time)` —— `SurviveTime` 在一局内只增不减，**回退 60 秒以上**就判定换局并清表
（留 60 秒余量是避免把"时间污染把显示时刻冻结成较小值"误判成换局）；`Clear()` 里把游标归零。
仍未做的是"事件驱动"的清理（挂 `ChangeGameState`），当前这种自愈式写法不依赖任何钩子、跨端一致。

## 12. 桶长可配置 + 身份污染按收件人（2026-10-19 深夜实现）

### 12.1 `[ClueMergeWindow] Seconds`（默认 30）

原版把桶长写死在 `Device.RecordLastUsingPlayer`（0.1.18 :166404，`surviveTime / 30 * 30`），
没法只改常量 ⇒ 本功能**门控式接管**：

| 配置 | 行为 |
| --- | --- |
| `30`（默认） | `MergeWindowHook` 直接放行 ⇒ 原版方法原样跑，**一行都不碰**（零风险） |
| `0` | 禁用合并：`ClueMergeWindow.LimitTime` 返回 `int.MaxValue` ⇒ 原版谓词 `x.Time >= limitTime` 永不成立 ⇒ 每次使用都追加一条 |
| 其它（如 60） | 自定义滚动桶长（`surviveTime / 秒数 * 秒数`） |

接管时逐字复刻原版（身份映射 `Anonymity→0 / Mastermind→11037 / Black→66613`、
`S_REMOVE_CLUE`＋`S_ADD_CLUE` 的顺序、`S_LEFT_CLUE{RoleFace}`），并显式补上两个 Postfix 的职责
（接管后它们不会跑）：`RecordDetailFeature.RecordHook.StampWhat`（字段 100）、
`ShadowSabotageFeature.StampPollution`（字段 101/103）。
⚠️ 优先级：污染 `Priority.First` → `RecordDetail` 默认 → 本钩子 `Priority.Low`（必须最后）。
⚠️ 一旦接管，无论成败**都不再让原版跑**（返回 false），避免"接管写一半 + 原版再写一条"。
我们的破坏点线索（`ShadowSabotage` 自建那条）走同一个 `ClueMergeWindow.LimitTime`。

### 12.2 身份污染：出站按收件人决定"实名 / 某人"

真值照旧写 `PlayerId = 0`（**"破坏时不覆盖破坏前"依赖它**），另记字段 **103 = 真实当事人**；
出站口 `HostPeerSession.Send` 的改写（`Wire.RewriteOutflow`）按收件人决定：

| 收件人 | 下发 `PlayerId` | 效果 |
| --- | --- | --- |
| 当事人本人（`收件人 == 103`） | **真实 pid** | 看自己的线索是**实名 + 自己头像** |
| 其他所有人（含房主自己、旁观者、死者） | `0` | 「某人」 |
| 未装本模块的端 | 同上（按收件人） | 一致（改的是包，不依赖对端） |

范围：只处理带 103 的线索；**角色线索 11037/11038/66613 永不改写**；没有 103 的正常线索一个字不改；
出站副本一律 `SetRealOwner(copy, 0)` —— 否则装了模块的"别人"能自己把当事人读出来。
覆盖的包：`S_SCAN_DEVICE`、`S_ADD_MY_CLUES`、`S_ADD_CLUE`、`S_REMOVE_CLUE`。
