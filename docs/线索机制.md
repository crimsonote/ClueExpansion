# 线索机制：真值在哪、污染怎么才能被看见

> 本文只讲**真值 / 包路径 / 污染可见性**。文本来源优先级、渲染路径、版本差异与决策记录在 `docs/线索管线.md`（含 §12 的桶长配置与「当事人看实名」逐条规则）。

本文回答两件事：**线索在每台机器上从哪读**、以及**我们的两条污染各自谁能看到**。
2026-10-18 夜逐行核对（0.1.18），并已按本文 §4 的方案落地时间污染。

## 1. 真值只有一份，但「界面上的时间」来自两条包

| 层 | 是什么 | 依据 |
| --- | --- | --- |
| **真值** | 服务端 `Server.Game.Device.ClueList`（每台设备一份 `List<PropositionInfo>`） | `0.1.18 :166249`，唯一写入点 `RecordLastUsingPlayer` :166386 |
| **死数据** | 客户端 `ClueMirror`（设备 → 线索镜像） | :180791；只被 `DeviceBase.HasDestroyableClue`（:5021-5038，**不读 Time**）与迁移快照 `ApplyClueLists`（:181503-181521）读，**UI 从不渲染它** |
| **界面时间（扫描）** | `S_SCAN_DEVICE` ← `Device.Scan` :166315，`InfoList.AddRange(ClueList.Where(!Destroyed))`（**按引用**） | :166318-166319 |
| **界面时间（平板 / 开场推送）** | `S_ADD_MY_CLUES` ← :174520-174540 | 每位存活玩家一包；无 `IsHost` 守卫 |

⇒ **改 `S_ADD_CLUE` / `S_REMOVE_CLUE` 不会影响任何界面显示**（它只喂 `ClueMirror` 这份死数据）。
这是 2026-10-18 夜里「黑幕破坏了但时间看起来完全没变」的直接原因。

房主分叉点只有三处 `IsHost` 短路：`Handle_S_ADD_CLUE` / `Handle_S_REMOVE_CLUE` / `Handle_S_CLEAR_CLUES`
（:43623 / :43632 / :43641）。**扫描与平板那两条包没有分叉** —— 房主自己也会收到
（`Session = HostPeerSession(LocalLoopbackSink)`，:177025-177032 / :162611-162630），
所以改这两条出站包**房主与远端一视同仁**。

## 2. 两条污染的可见性（现状）

| 污染 | 落地方式 | 真值 | 远端（装了 / 没装） | 房主自己 |
| --- | --- | --- | --- | --- |
| **身份**（`PlayerId → 0`） | `RecordLastUsingPlayer` 的 Prefix 把 `state` 改 `Anonymity`（写在**真值**上） | `PlayerId = 0` | 看到「某人」 | 看到「某人」 ✅ |
| **时间**（`Time → 冻结时刻`） | 写入时打标（未知字段 **101** = 显示时刻）+ 出站副本替换（真值的 `Time` **不动**） | 真实时间 + 101 | 看到冻结时间 | 看到冻结时间 ✅ |

## 3. 为什么时间污染不能直接改真值

`RecordLastUsingPlayer` 的 30 秒去重窗口（:166404-166437）：

```
limitTime = surviveTime / 30 * 30
命中条件：x.Time >= limitTime && x.PlayerId == playerId && !x.Destroyed
命中 ⇒ S_REMOVE_CLUE(旧克隆) → 改 Time → S_ADD_CLUE(新克隆)     // 合并
未命中 ⇒ 追加新条目                                             // 同一设备会多出一行
```

冻结时刻**永远落在旧桶**（`frozen < limitTime`）⇒ 命中条件恒不成立 ⇒ 每次操作都追加一行，
平板主列表（:54839-54879）出现重复卡。⇒ 所以只能「另存显示时刻 + 出站替换」。

## 4. 已落地的方案（A′：写时打标 + 出站统一改写）

1. **打标**：`Features/Host/ShadowSabotage/Patch.cs` 的 `DisplayTimeStampHook`
   （`RecordLastUsingPlayer` 的 **Postfix**，`Priority.Last`）—— 时钟破坏点已破坏期间，
   把本设备 `ClueList` 里 `Time == 当刻 SurviveTime && RoomId == 本房间 && !Destroyed` 的条目
   写上 `UnknownFields.SetDisplayTime(info, FrozenTime)`。
2. **出站替换**：同文件的 `DisplayTimeOutflowHook`（`Server.Game.HostPeerSession.Send(IMessage)` 的 Prefix，
   public，:175626）—— 只对 `S_SCAN_DEVICE` / `S_ADD_MY_CLUES` 生效，
   由 `Wire.RewriteDisplayTime` **先克隆**带标记的条目再换 `Time`，其余条目按引用放进新包。
   改写后走 `__instance.Underlying.Send(...)` 并返回 `false`（避免重入 Prefix）。
3. **删掉**旧的 `TimePolluteBroadcastHook`（改 `S_ADD_CLUE`/`S_REMOVE_CLUE`）与
   `TimePolluteScanHook`（整替 `Device.Scan`）：前者对界面无效，后者被 `TimePollutionOn` 的 Survive 门
   挡着（扫描只发生在调查阶段）且会整批冻结旧线索。
4. `Core/UnknownFields.cs`：新增 `DisplayTimeFieldNumber = 101` +
   `SetDisplayTime/GetDisplayTime` + 通用 `ReplaceValue`（覆盖写，避开 varintList 的追加语义）。

**怎么在实机确认它生效**（日志里两行）：

```text
[ClueDetail] 破坏点[时钟记录组件] 破坏生效：身份污染=关，时间污染=开（冻结在 529 秒）。
[ClueDetail] 破坏点：出站改写 N 条线索的显示时间为冻结时刻（S_ADD_MY_CLUES）。   ← 只在真的改过时打
```

第二行出现 ⇒ 平板 / 扫描里那条线索的**时间列**应显示成「破坏那一刻」（冻结值），
而报告里的死亡时间、30 秒去重、迁移快照都不受影响。

**为什么这条通道合规**：我们只改**出站副本**里的 `Time` —— 未装本模块的客户端也会看到冻结时间
（`AGENTS.md` §4 例外备案），而真值、30 秒去重、迁移快照都不受影响。

**已知代价 / 边界**：

- 迁移（host migration）：迁移快照读的是 `ClueMirror`（`S_ADD_CLUE` 的副本，**不含 101 标记**），
  所以迁移后新主机对**迁移前**写下的线索不再冻结显示；迁移后新写的照常。
- 房主侧 `ClueWhat` 的第 ②.5 级来源（按 `(PlayerId, Time, RoomId)` 查 `DetailStore`）会因显示时间被换成
  冻结值而**查不到**；但第 ① 级「包内未知字段 100」通常仍然命中（`RecordDetail` 写在服务端条目上，
  我们的克隆把它一起带出去）⇒ 一般无感；只有在 100 缺失时（例如房主关了 `RecordDetail`）才会退化到
  「设备关联 / 房间推断」。远端不受影响。
- 时间冻结后，客户端线索按 `Time` 排序（`Clue.CompareTo`，:27536-27539）会与真实顺序不同 ——
  这正是「时间被冻结」的表现，已接受。

## 5. 其余已确认的相关事实

- **扫描下发**按引用（`AddRange`）；所以出站改写**必须克隆**，否则会写坏真值。
- **客户端一次性扫描标记**：`DeviceBase.Scan` :4952 → `Managers.Game.ScannedDeviceSet.Add(ID)`，每局每设备一次。
- **跨局清空**：`Device.StartSurvival` :166516 会 `ClueList.Clear()` + 广播 `S_CLEAR_CLUES`；
  `StartDetective` :166531 按 `ClueList.Count` 决定 `Bubble`（有线索 ⇒ `-1`，即可调查）。
- **`Bubble = -1` 与按 E 互斥**：`DeviceBase.InteractBase` :4843 第一优先就是「调查」，
  所以 Survive 期间必须保持 `Bubble == 0`（破坏点不自己设，交给 `StartDetective`）。
- **本模块自己的线索子系统**（`Core/DetailStore.cs` 房主旁路表、`Core/ClueWhat.cs`、
  `Features/Host/RecordDetail/`、`Features/Client/ClueRender|ClueCard/`）走「未知字段 100 + 旁路表」，
  与上面两条污染的可见性互不影响；排查"卡片显示不对"时先开 `[ClueRenderDetail] LogResolution` 看来源。
