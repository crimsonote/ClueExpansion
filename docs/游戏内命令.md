# 游戏内命令（聊天框）—— `Features/Host/GameChat/`

在**游戏自带的聊天框**里敲 `/` 开头的命令。房主侧实现，**客户端不需要装本模块**。

---

## 1. 命令一览

| 命令 | 语法 | 可用阶段 | 谁能用 |
| --- | --- | --- | --- |
| `/say` | `/say <昵称\|座位号> <消息>` | **大厅 / 会议** | 所有玩家 |
| `/clue` | `/clue [条件...]` | **仅会议** | 所有玩家（只搜自己的线索） |
| `/who` | `/who` | 任意 | 所有玩家（列出 ID 与昵称，给 `/say` 用） |
| `/help` | `/help` | 任意 | 所有玩家 |

### 1.1 `/say` —— 私聊

只送达**发送者与目标**两个人，文字前缀 `[私聊]`。

目标解析（`Logic.cs` 的 `FindTarget`）：
1. 纯数字 → 按**座位号**（`PublicInfo.PlayerId`）精确匹配；
2. 否则按昵称：先**大小写不敏感全等**，再退到**包含**匹配（取第一个）。

⚠️ 私聊不是原版的"密聊频道"：它用的是普通聊天包，只是**只发给两个人**。
原版 `SecretChat`（发信机密聊，仅黑方）不受影响，也不走这条。

**死者规则（2026-10-21）**：

- **不能私聊死者** —— 死者的聊天框收不到存活玩家的私聊，包送过去也没人读，
  发送者却会以为"已经说到了"，所以直接回执拒绝；
- **死者发起的私聊标 `IsDead = true`**（原版 `S_CHAT_MESSAGE.IsDead`，客户端按死者样式渲染），
  否则接收方会当成活人说的话；
- 死者用 `/clue`、`/who`、`/help` 收到的回执同样按死者消息渲染。

### 1.2 `/clue` —— 检索自己搜集到的线索

只在**会议阶段**可用（其它阶段回一句「线索搜索只在会议阶段可用。」）。

条件语法（空格分隔 = **同时满足**）：

| 写法 | 含义 |
| --- | --- |
| `t:7:00am-7:30am` | 时间段（也接受游戏内显示的 12 小时制） |
| `t:>420` / `t:<560` | 时间的比较（单位=秒；420 = 7:00am） |
| `p:昵称` | 按玩家筛选 |
| `r:房间` | 按房间筛选 |
| `a:活动` | 按详细活动筛选 |
| `id:3` | 按玩家 ID **精确**筛选（昵称重名 / 生僻字时用，编号见 `/who`；污染期口径见 §7.1） |
| `-词` | **排除**包含该词的条目 |
| 裸词 | 全文匹配 |

`/clue help` 会回一份语法提示。

结果按 3 行一条拆成多条聊天消息（见 §3.2），首行是 `【我的线索】共 N 条` 或 `【搜索结果】命中 N 条`。

### 1.3 `/who` —— 列出玩家 ID 与昵称

给 `/say` 查名字用：列出全场玩家的**座位号与昵称**，昵称太长的会被 `MaxLineWidth` 折行。

### 1.4 `/help` —— 报到式帮助

只发**本模块**的命令清单，**不吞**（`return true`）—— 链上后面的模块（如捉迷藏）会继续报它自己的帮助，
所以玩家能看到**所有装了命令的模块**的帮助。

⚠️ 但"不吞"意味着原版会把它当普通聊天**广播给全服**（实机截图里就是这样）。
所以另有一个兜底补丁挂在 `ServerGameHostPacketHandler.RelayNormalChat`：

- **有人吞就轮不到它**（我们是 `Priority.First`，先报到）；
- **没人吞就由我们兜底吞掉**，且**只拦完全等于 `/help`** 的文本（允许前后空白），
  其它 `/` 开头的文本一律放行，不给别的模块的命令添麻烦。

### 1.5 `MaxLineWidth` —— 折行宽度

配置项 `[GameChat] MaxLineWidth`（默认 **50**，范围 20–200）。

**显示宽度**算法：中文（全角）算 2，ASCII 算 1。超宽的部分折到下一行，**折出来的行同样计入
“每条消息最多 3 行”的上限**。

为什么需要它：聊天气泡宽度固定，超出的部分会被 TMP **直接截断**——实机截图里就出现过
「…最后被识别于身份验证屏幕」被切掉的情况，所以先折行再按 3 行打包。

## 2. 机制依据

### 2.1 为什么必须做在服务端

私聊要控制**收件人**（只发两个人），只能在房主进程里拦下原始聊天包、再用
`player.Session.Send(...)` 单发。

挂载点：`Server.Game.HostPacketHandler.Handle_C_CHAT_MESSAGE`（0.1.18 :177661，`public static`）。
形参是 `(IPacketSink session, Packet packet)`，从 `session as HostPeerSession` 拿 `Player`。

### 2.2 只处理 `NormalChat`

`C_CHAT_MESSAGE.Type` 有 `NormalChat` / `DeviceChat` / `SecretChat`：

- `DeviceChat` / `SecretChat` 是**发信机**频道，原版逻辑里带着占用判定、密聊黑方闸门、冷却时间
  ⇒ 本模块**一律放行**（`return true`），一个字节不动。

### 2.3 颜色：服务端做不到

客户端 `Handle_S_CHAT_MESSAGE` 会先调 `Util.NeutralizeRichText`（0.1.18 :43911）把 `<`
换成 `<`+零宽字符 ⇒ **任何 `<color=…>` 都会失效**。所以标注一律用**纯文本**（如 `[私聊]`）。

## 3. 与其它模块共存（三条约定，2026-10-19 定案）

1. **只认领自己的命令名**：名字不在 `{say, clue, help}` 里 ⇒ `return true` 放行，
   别人的命令原样流过去；
2. **认领了就吞**：处理完 `return false`，命令不会变成聊天广播；
3. **`/help` 只报到不吞**：发完自己的帮助 `return true`，让后面的模块继续报到。

⚠️ **`[HarmonyPriority(Priority.First)]` 是必需的**：捉迷藏的游戏内命令也挂在同一个方法上
（默认 `Normal` 优先级）且会吞掉 `/help`；我们必须**先**报到，它才能继续报它的。

### 3.1 主线程

Prefix 里**只做"要不要拦"的判断**（不碰 Unity API），真正的分发经
`room.Push(delegate { Dispatch(...); })` 排到主线程 —— 与 `ServerGameRoom.SurvivalTick` 同一线程。

### 3.2 单条消息最多 3 行

`GameChatFeature.MaxLinesPerMessage = 3`，与捉迷藏的 `MaxLinesPerMessage` 是同一条硬约束：
原版聊天预制体按 3 行排版，超了会被截断或撑破布局。所以长文本（`/clue` 结果、`/help`）必须
**按 3 行一段拆成多条消息依次发**（`SendLines`）。

## 4. 会议自动线索报告（`Report.cs`）

除命令外，本功能还有一条**自动**行为：**进入会议（`Trial`）时**，给每个玩家各发一份
**他自己的**线索报告（不是广播，别人看不到）。

- 窗口：`[案件时间 - 20 秒, 案件时间]`；
  `ReportWindowSeconds = 20` —— 用户口径「游戏内时钟 20 分钟 = 20 秒」
  （`FormatTimeSentence` :27278 里 `小时 = time/60`，所以 1 游戏小时 = 60 秒）；
- 案件时间取服务端 `GameRoom.CorpseMetas`（:172596）里的 `DeadTime`：
  优先"已报告 / 已发现"的那具，否则取最早死亡的那具（即原版"模糊时间"的来源）。

---

## 5. 线索索引（`ClueIndex.cs`）

`/clue` 与会议报告共用的数据源：**逐人线索表** `pid → (线索键 → 快照)`。

- 快照字段：`PlayerId` / `Time`（**显示时刻优先**，即被时间污染冻结的那个值）/ `RoomId` /
  `What`（`EWhatType`，0 = 未知）/ `Line`（已渲染成一行）/ `Key`（去重键 `玩家:时间:房间`）；
- 去重键与客户端 `AlreadyExistClue` 的原版口径一致（`PlayerId` + `RoomId` + `Time`）。

## 6. 已知限制

| 限制 | 说明 |
| --- | --- |
| 无颜色 | 客户端 `NeutralizeRichText` 会杀掉所有富文本（§2.3） |
| 单条 3 行 | 超长内容拆成多条，玩家会看到连续几条消息（§3.2） |
| `/clue` 仅会议 | 有意为之：避免在生存阶段用命令变相"共享线索" |
| 只认 `NormalChat` | 发信机频道不参与（§2.2） |
| 名称冲突 | 别的模块若也用 `say`/`clue`/`who`/`help` 且**优先级高于 `First`**，会先被它吞掉 |
| 折行是"估算" | `MaxLineWidth` 按中文 2 / ASCII 1 估算，不读 TMP 的真实排版宽度（够用但不精确）|
## 7. 2026-10-20 变更

### 7.1 `/clue` 新增 `id:` 精确搜索

```
/clue id:3            # 只列 PlayerId = 3 的线索
/clue id:3 r:广播室    # 可与其它条件叠加
```

- 判据是**精确相等**，不是模糊匹配；后者是 `p:` 的职责（`p:` 走 `WhoOf` 的显示名）。
- **污染行对非当事人不参与 `id:` 匹配**（2026-10-20 收紧）。渲染层 `WhoOf` 对非当事人
  一律显示「某人」，而检索层原来直接比真值与字段 103 ⇒ 非当事人逐个 id 试就能把「某人」
  的真身反查出来，身份破坏点等于白做。现在两层同口径：
  当事人自己（`RealOwner == viewerId`）照常按真实 id 搜得到；其他人只能按**看得见的那个编号**搜
  （嫁祸档的 `11037` / `66613` 仍可命中），想看全部匿名记录用 `p:某人`。
  实现见 `ClueIndex.cs` 的 `Matches`（`visibleId`）。

### 7.2 `/clue help` 改成 3 个气泡

早前是 3 行挤一个气泡（`id:` 与 `page:` 没处写），后来改成 4 条单行（又太散）。
现在把 9 行交给 `PackBubbles` 按 3 行/气泡自动打包，正好 3 个气泡、一个气泡一个主题：

```text
【/clue 用法】仅会议可用 ｜ 空格 = 同时满足
/clue t:7:00am-7:30am p:3 r:广播室 a:点燃
无条件只报总数 ｜ -词 排除 ｜ 条件可任意叠加
```

```text
t: 时间段 7:00am-7:30am ｜ 比较 t:>420（单位秒）
p: 昵称，模糊匹配 ｜ id: 玩家ID，精确相等
id: 适合昵称重名或生僻字，编号用 /w 查
```

```text
r: 房间 ｜ a: 详细活动 ｜ 裸词 = 全文匹配
例：/clue r:电脑室 -被 ｜ /clue a:点燃 p:3
翻页：在查询后加 page:2 ｜ 语法：/c help
```

按 `MaxLineWidth = 50` 量过，最宽 48 ⇒ 默认配置下不折行，9 行就是 3 个气泡。
⚠️ 若把 `MaxLineWidth` 调小，`PackBubbles` 会重新折行，气泡数可能变成 4 个以上 —— 这是预期行为。

### 7.3 `/help` 的广播兜底**终于挂上了**

`HelpBroadcastGuard` 原先嵌套在 `ChatCommandHook` 里（二级嵌套），装载器
`FeatureLoader.MountPatches` 只认 `DeclaringType == featureType` 的一层嵌套
⇒ **从来没挂载过**，`/help` 一直照常进公聊。现已提到 `GameChatFeature` 直接嵌套。

⚠️ 教训与 AGENTS.md §11.7 同源：**「失败 0」不代表挂上了**，唯一可靠判据是启动日志的
`补丁 N 个`，以及 Cecil 里看 `HelpBroadcastGuard` 的 `DeclaringType` 是不是 `GameChatFeature`。

### 7.4 时间维度为什么**没有**同类问题

`id:` 之所以漏，是因为**一个字段有两个来源**（真值 `PlayerId` + 字段 103），检索层自己挑了真值。
时间没有第二来源：`ClueRow` 在构造时就把 `Time` 定死了 ——

```csharp
int display = UnknownFields.GetDisplayTime(info);
Time = display != 0 ? display : info.Time;
```

（`ClueIndex.cs` 两处：扫描登记 `RememberScan` 与设备真值 `CollectFromDevices`。）之后

- 渲染 `ClockOf(row.Time)`、
- `t:` / `t:>420` / 会议报告的 `t:from-to`（`Matches` 的 `TimeMin` / `TimeMax`）、
- 排序 `matched.Sort((a, b) => a.Time…)`、

**全部共用这一个值**。真值 `info.Time` 只用于去重键 `KeyOf`（不显示、不参与检索）。

⚠️ 以后别照着 `id:` 的模式去"修"时间：`Matches` 里**没有**第二个时间来源可挑，
把 `info.Time` 引进来才会**重新打开**泄露。

已知副作用（不是漏洞）：冻结后污染期线索显示同一时刻 ⇒ `/clue` 的先后顺序退化成插入顺序
（= 真实先后）。未装插件的客户端 `ClueList.Sort` 对相等 `Time` 同样保持原顺序，行为一致，
所以这不是本模块引入的信息。
